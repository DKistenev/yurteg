## 1. Введение

«ЮрТэг» — десктопное приложение для автоматизированной обработки, анонимизации и систематизации архивов юридических документов с использованием локального искусственного интеллекта. Система предназначена для юристов, работающих с большими объёмами договорной документации.

Ключевое отличие Системы от аналогичных решений — обработка документов выполняется полностью локально, на компьютере пользователя, с использованием собственной файнтюненной языковой модели. Персональные данные не покидают устройство.

Система разработана методом вайб-кодинга: команда из трёх студентов-юристов, не обладающих профессиональными навыками программирования, создала полнофункциональное десктопное приложение с помощью AI-ассистента Claude Code.

**Текущая версия:** 1.0.0
**Репозиторий:** https://github.com/DKistenev/yurteg
**Платформа:** macOS (нативное приложение)

## 3. Назначение и цели создания Системы

### 3.1. Назначение

Система предназначена для автоматизации рутинного процесса обработки архивов юридических документов: извлечения ключевой информации, классификации, организации файлов в структурированные каталоги с отслеживанием версий, платежей и сроков действия. Система обеспечивает конфиденциальность данных за счёт локальной обработки с использованием собственной файнтюненной модели и локальной анонимизации текста перед обращением к облачным AI-сервисам.

### 3.2. Цели

- Сократить время обработки архива из 100+ договоров с нескольких часов ручной работы до нескольких минут автоматической обработки.
- Обеспечить единообразную классификацию документов по типу, контрагенту, предмету и ключевым параметрам.
- Автоматически создать структурированную файловую систему из хаотичного архива документов.
- Гарантировать конфиденциальность: персональные данные не покидают компьютер пользователя благодаря локальной обработке. Архитектура предусматривает подключение облачных провайдеров с предварительной анонимизацией (планируется).
- Обеспечить управление жизненным циклом документов: отслеживание сроков действия, версий, платежей.
- Создать инструмент, доступный юристам без технической подготовки: нативное десктопное приложение с автоматической настройкой при первом запуске.

## 4. Общая архитектура Системы

### 4.1. Архитектурные слои

Система построена по модульной архитектуре с чётким разделением на слои:

| Слой | Компоненты | Ответственность |
|------|-----------|-----------------|
| **Представление (UI)** | `app/main.py`, `app/pages/`, `app/components/` | Нативное десктопное приложение NiceGUI, навигация, визуализация |
| **Состояние** | `app/state.py` | Типизированное хранение состояния сессии (AppState dataclass) |
| **Контроллер** | `controller.py` | Оркестрация пайплайна обработки, параллелизация AI-запросов |
| **Модули обработки** | `modules/scanner.py`, `extractor.py`, `anonymizer.py`, `ai_extractor.py`, `postprocessor.py`, `organizer.py` | Каждый этап пайплайна — отдельный модуль с чётко определённым интерфейсом |
| **Провайдеры AI** | `providers/ollama.py`, `zai.py`, `openrouter.py` | Абстракция над AI-моделями, единый интерфейс `LLMProvider` |
| **Сервисы** | `services/` | Бизнес-логика: версионирование, платежи, шаблоны, клиентское управление, жизненный цикл |
| **Данные** | `modules/database.py`, `modules/models.py` | SQLite, миграции, типизированные модели данных |

### 4.2. Пайплайн обработки

Последовательность обработки одного файла:

```
ВХОДНАЯ ДИРЕКТОРИЯ
       ↓
1. SCANNER (scan_directory)
   ├── Рекурсивный поиск PDF/DOCX
   ├── Вычисление SHA-256 хеша
   └── Проверка размера (< 50 МБ)
       ↓
2. DATABASE (проверка кеша)
   └── Пропуск, если файл уже обработан (совпадение хеша)
       ↓
3. EXTRACTOR (extract_text)
   ├── PDF → pdfplumber (постраничное извлечение)
   ├── DOCX → python-docx (параграфы + таблицы)
   └── Определение сканированных PDF (< 50 символов/страница)
       ↓
4. ANONYMIZER (anonymize)
   ├── NER (Natasha) — трёхпроходная стратегия
   ├── Регулярные выражения для 9 категорий ПД
   └── Словарь замен для деанонимизации
       ↓
5. AI EXTRACTOR (extract_metadata) — ПАРАЛЛЕЛЬНО через ThreadPoolExecutor
   ├── Провайдер: Ollama (локальная файнтюненная модель)
   ├── Запрос с GBNF-грамматикой → гарантированный JSON в заданной схеме
   ├── Постобработка: sanitize_metadata (для локальной модели)
   └── Вычисление уверенности через logprobs
       ↓
6. POSTPROCESSOR (sanitize_metadata)
   ├── Профили полей: cyrillic_only, cyrillic_latin, enum, date, number, boolean
   ├── Нормализация дат в ISO 8601
   └── Защита аббревиатур (NDA, ООО, ИП, ЗАО и др.)
       ↓
7. ORGANIZER (organize_file)
   ├── Копирование в Документы/{Тип}/{Контрагент}/
   └── Генерация имени файла
       ↓
8. DATABASE SAVE (save_result)
   ├── UPSERT по file_hash
   ├── Вычисление эмбеддингов (при включении)
   └── Извлечение платежей, связывание версий
```

### 4.3. Модель параллелизации

- **Быстрый путь (последовательно):** извлечение текста + анонимизация (< 0.1 сек/файл)
- **Узкое место (параллельно):** AI-извлечение метаданных через ThreadPoolExecutor (до 5 воркеров, ~4 сек/файл)
- **Финализация (последовательно):** организация + сохранение (< 0.1 сек/файл)

## 5. Функциональные требования

### 5.1. Модуль сканирования файлов

Система рекурсивно сканирует выбранную пользователем директорию и все вложенные папки.

- **Поддерживаемые форматы:** PDF (.pdf), Microsoft Word (.docx)
- **Ограничение размера:** не более 50 МБ на файл
- **Дедупликация:** для каждого файла вычисляется SHA-256 хеш; файлы с известным хешем (status=done) пропускаются
- **Пропуск неподдерживаемых форматов** с записью в лог

### 5.2. Модуль извлечения текста

Для каждого файла Система извлекает текстовое содержимое:

- **Электронные PDF** — библиотека pdfplumber, постраничное извлечение с сохранением структуры абзацев
- **Документы DOCX** — библиотека python-docx, извлечение текста из параграфов и таблиц

Определение типа PDF выполняется автоматически: если средний объём извлечённого текста составляет менее 50 символов на страницу, файл классифицируется как «сканированный» и пропускается с соответствующим предупреждением.

Тексты длиной более 30 000 символов (~7 500 токенов) усекаются перед отправкой в AI-модуль. Факт усечения фиксируется в поле `was_truncated`.

### 5.3. Модуль анонимизации

Перед отправкой текста в облачный AI-провайдер Система выполняет локальную анонимизацию персональных данных. Анонимизация выполняется на устройстве пользователя; анонимизированный текст не сохраняется на диск.

При использовании локальной модели (Ollama) анонимизация не применяется — данные не покидают устройство. Однако анонимизированная копия текста подготавливается на случай переключения на облачный fallback-провайдер.

#### Данные, подлежащие замене

| Тип данных | Метод обнаружения | Маска |
|------------|-------------------|-------|
| ФИО физических лиц | NER-модель Natasha (трёхпроходная стратегия) | `[ФИО_1]`, `[ФИО_2]`, ... |
| Телефонные номера | Регулярное выражение | `[ТЕЛЕФОН_1]`, `[ТЕЛЕФОН_2]`, ... |
| Адреса электронной почты | Регулярное выражение | `[EMAIL_1]`, `[EMAIL_2]`, ... |
| Паспортные данные | Контекстный поиск (серия + номер рядом с ключевыми словами) | `[ПАСПОРТ_1]`, ... |
| СНИЛС | Регулярное выражение + валидация контрольной суммы | `[СНИЛС_1]`, ... |
| ИНН физических лиц | 12 цифр подряд, не в контексте организации | `[ИНН_ФЛ_1]`, ... |
| ИНН юридических лиц | 10 цифр с префиксом «ИНН:» | `[ИНН_ЮЛ_1]`, ... |
| ОГРН | 13 цифр с префиксом «ОГРН:» | `[ОГРН_1]`, ... |
| КПП | 9 цифр с префиксом «КПП:» | `[КПП_1]`, ... |
| Банковские реквизиты | 20 цифр с контекстом (р/с, к/с) | `[СЧЁТ_1]`, ... |
| ИП (индивидуальный предприниматель) | Паттерн «ИП Фамилия Имя Отчество» | `[ИП_1]`, ... |

#### Данные, которые НЕ анонимизируются

- Наименования юридических лиц (необходимы для классификации)
- Даты (необходимы для метаданных)
- Суммы и валюты (необходимы для метаданных)

#### Трёхпроходная стратегия NER

1. **Проход 1 — Оригинальный текст:** Natasha NER на исходном тексте для извлечения персон (тег PER)
2. **Проход 2 — Нормализованный текст:** вставка точек перед структурными метками (`Телефон:`, `Паспорт:`) для улучшения сегментации NER
3. **Проход 3 — Восстановление после OCR:** обнаружение разнесённых по буквам имён (`И в а н о в`), сжатие и повторный запуск NER

#### Контекстная фильтрация

- СНИЛС: валидация контрольной суммы или наличие контекстных ключевых слов
- Телефоны: исключение, если являются частью 20+-значного банковского счёта
- ИНН: исключение, если находится в денежном контексте (сумма, цена)
- Паспорт: исключение в техническом контексте (`технический паспорт`)

#### Управление анонимизацией

Пользователь может выбрать типы персональных данных для анонимизации через интерфейс настроек. Параметр `enabled_types` позволяет включить или отключить маскирование отдельных категорий.

**Принцип анонимизации — консервативный:** в спорных случаях предпочтительнее анонимизировать данные, нежели пропустить.

### 5.4. AI-провайдер: локальная модель

Система использует локальную файнтюненную модель для извлечения метаданных. Обработка выполняется полностью на устройстве пользователя без обращения к внешним сервисам.

#### Архитектура провайдеров

Система реализует абстракцию над языковыми моделями через единый интерфейс `LLMProvider`:

```
LLMProvider (абстрактный класс)
├── complete(messages, **kwargs) → str
├── verify_key() → bool
└── close() → None
```

В текущей версии используется единственный провайдер — **Ollama** (локальный инференс через llama-server). Архитектура допускает подключение облачных провайдеров (ZAI, OpenRouter) в качестве резервных — код написан и протестирован, но в текущей версии не активирован, поскольку локальная модель полностью покрывает потребности.

#### Локальная модель (Ollama)

Система включает собственную файнтюненную модель:

- **Базовая модель:** QWEN 2.5 1.5B
- **Метод обучения:** LoRA-файнтюнинг на юридических документах
- **Формат:** GGUF (Q4_K_M квантизация), ~1.5 ГБ
- **Хостинг модели:** HuggingFace (`SuperPuperD/yurteg-1.5b-v3-gguf`)
- **Инференс:** llama.cpp (сборка b5606)

Двухзапросная стратегия для Ollama:
1. **Запрос 1:** с GBNF-грамматикой → гарантированный JSON в заданной схеме
2. **Запрос 2** (при подозрительных null-значениях): с `logprobs=True` → вычисление уверенности

#### Вычисление уверенности (confidence)

Среднее значение logprobs из второго запроса нормализуется линейно: `(mean + 4.0) / 4.0`, результат в диапазоне [0.0, 1.0]. Порог: raw < −2.0 → confidence < 0.5 → документ помечается для ручной проверки.

### 5.5. Модуль AI-извлечения метаданных

Текст договора отправляется в локальную языковую модель для извлечения структурированных метаданных. GBNF-грамматика гарантирует, что ответ возвращается строго в формате JSON с заданной схемой полей, что заменяет необходимость в отдельном модуле валидации структуры.

#### Извлекаемые метаданные

| Поле | Тип | Описание | Пример |
|------|-----|----------|--------|
| `contract_type` | string | Тип документа | Договор поставки |
| `counterparty` | string | Наименование контрагента | ООО «Ромашка» |
| `subject` | string | Предмет договора (1–2 предложения) | Поставка офисной мебели |
| `date_signed` | string (ISO) | Дата подписания | 2024-03-15 |
| `date_start` | string (ISO) | Дата начала действия | 2024-04-01 |
| `date_end` | string (ISO) | Дата окончания действия | 2025-03-31 |
| `amount` | string | Сумма договора с валютой | 1 500 000 руб. |
| `special_conditions` | string[] | Особые условия | ["Неустойка 0.1% за день просрочки"] |
| `parties` | string[] | Все стороны договора | ["ООО А", "ООО Б"] |
| `contract_number` | string | Номер договора | № 123/2024 |
| `confidence` | float | Уверенность модели (0–1) | 0.85 |
| `is_template` | boolean | Является ли документ шаблоном (бланком) | false |
| `payment_terms` | string | Условия оплаты | Ежемесячно до 5-го числа |
| `payment_amount` | float | Сумма платежа (числовое значение) | 150000.0 |
| `payment_frequency` | enum | Периодичность | monthly / quarterly / yearly / once |
| `payment_direction` | enum | Направление | income / expense |

#### Обработка ответа

- Парсинг JSON из ответа модели с извлечением из markdown-блока ` ```json `, из блоков `<think>...</think>` (thinking-модели), и из произвольных `{...}` конструкций
- При невалидном JSON — повторный запрос (до 3 попыток)
- Нормализация дат: русские форматы (`31 декабря 2025 г.`, `31.12.2025`) → ISO 8601 (`2025-12-31`)
- Валидация диапазона дат: только 1990–2099

### 5.6. Модуль постобработки

Модуль `postprocessor.py` выполняет санитизацию ответов локальной модели по профилям полей. Постобработка применяется к ответам Ollama-провайдера, поскольку локальная модель (1.5B параметров) может генерировать артефакты в строковых полях:

| Профиль | Поля | Обработка |
|---------|------|-----------|
| `cyrillic_only` | contract_type, special_conditions | Только кириллица + цифры + пунктуация; аббревиатуры (NDA, SLA, ООО, ИП, ЗАО) защищены от удаления |
| `cyrillic_latin` | counterparty, parties, subject, amount, payment_terms | Кириллица + латиница + цифры + пунктуация |
| `enum` | payment_frequency, payment_direction | Значение из допустимого множества; иначе → null |
| `date` | date_signed, date_start, date_end | Формат YYYY-MM-DD; иначе → null |
| `number` | confidence, payment_amount | Приведение к float; иначе → null |
| `boolean` | is_template | True/false или строковые эквиваленты |

Null-подобные строки (`"None"`, `"null"`, `""`, `"N/A"`) приводятся к Python `None`.

### 5.7. Обеспечение качества извлечения

Корректность извлечённых метаданных обеспечивается на нескольких уровнях:

- **GBNF-грамматика** гарантирует структурную валидность JSON-ответа: все обязательные поля присутствуют, типы данных соблюдены, массивы и строки корректны. Это устраняет необходимость в отдельном модуле структурной валидации — модель физически не может вернуть невалидный JSON.
- **Постобработка** (§5.6) нормализует даты, перечисления и строковые поля, удаляя артефакты генерации.
- **Уверенность (confidence)** вычисляется через logprobs (§5.4) и отображается в интерфейсе, позволяя пользователю оценить надёжность результата.
- **Дедупликация по SHA-256** предотвращает повторную обработку уже обработанных файлов.

### 5.8. Модуль организации файлов

Система создаёт структурированную файловую систему на основе извлечённых метаданных:

```
Документы/
├── {Тип договора}/
│   ├── {Контрагент}/
│   │   ├── договор_поставки_ромашка_2024-03-15.pdf
│   │   └── ...
```

- **Только копирование.** Исходные файлы не модифицируются, не перемещаются и не удаляются.
- **Три режима группировки:** по типу (`type`), по контрагенту (`counterparty`), комбинированный (`both`, по умолчанию)
- **Генерация имени файла:** `{тип}_{контрагент}_{дата}.{расширение}`
- **Санитизация имён:** удаление спецсимволов, ограничение 80 символов
- **Конфликты:** суффикс `_1`, `_2` и т.д.
- **Неклассифицированные файлы** помещаются в отдельную папку

### 5.9. Версионирование документов

Система отслеживает версии одного и того же контракта:

- Автоматическая группировка документов по семантической близости через эмбеддинги (sentence-transformers)
- Ручная привязка версий через интерфейс
- Визуальное сравнение (редлайн) между версиями через `redline_service`
- Таблица `document_versions` с отслеживанием номеров версий и связей

### 5.10. Управление платежами и дедлайнами

- Автоматическое извлечение платёжных параметров из метаданных: сумма, периодичность, направление (доход/расход)
- Отслеживание дат оплаты в таблице `payments`
- Предупреждения об истечении сроков действия договоров (настраиваемый порог, по умолчанию 30 дней)
- Календарное представление сроков в интерфейсе

### 5.11. Шаблоны и сравнение

- Загрузка эталонных шаблонов договоров (PDF) через интерфейс
- Привязка шаблонов к типам договоров
- Автоматическое сравнение обработанного документа с шаблоном для выявления отклонений
- Кеширование эмбеддингов шаблонов в таблице `template_embeddings`

### 5.12. Мульти-клиентское управление

- `ClientManager` связывает контрагентов с клиентскими папками
- Каждый клиент может иметь собственную базу данных SQLite
- Привязка инициируется пользователем через интерфейс реестра (не автоматически)
- Перемещение записей между клиентскими БД

### 5.13. Telegram-интеграция (подготовлено, не развёрнуто)

Серверный компонент (`bot_server/`) для удалённой загрузки документов через Telegram написан и протестирован, но в текущей версии не подключён к десктопному приложению. Развёртывание планируется в следующей версии.

Архитектура компонента:
- Команда `/start` → генерация 6-значного кода привязки (действителен 15 минут)
- Пользователь вводит код в настройках десктопного приложения
- Отправка файла в Telegram → валидация привязки → помещение в очередь обработки
- Фоновый планировщик (`APScheduler`) обрабатывает файлы из очереди

## 9. Нефункциональные требования

### 9.1. Производительность

- Обработка одного файла (без учёта AI-инференса): не более 1 секунды
- AI-инференс: ~4 секунды/файл (локальная модель)
- Обработка архива из 100 файлов: не более 15 минут (при 5 параллельных воркерах)
- UI не зависает во время обработки: AI-запросы выполняются в отдельных потоках через `ThreadPoolExecutor`

### 9.2. Надёжность

- Сбой на одном файле не прерывает обработку всего архива
- Все ошибки логируются с деталями (тип ошибки, имя файла, traceback)
- Резюмируемость: при повторном запуске — продолжение с места остановки
- Тройная защита при завершении: `app.on_shutdown`, `app.on_disconnect`, `atexit.register` — гарантированная остановка llama-server
- Блокировка единственного экземпляра (`instance_lock.py`): предотвращение запуска нескольких копий приложения

### 9.3. Удобство использования

- Установка: скачать .dmg, перетащить в Applications, запустить
- Первый запуск: автоматическая настройка (скачивание модели, запуск llama-server)
- Не требует знаний программирования
- Обучающий тур для новых пользователей
- Понятные сообщения об ошибках на русском языке

### 9.4. Безопасность и конфиденциальность

- **Полностью локальная обработка:** все данные обрабатываются на устройстве пользователя, персональные данные не покидают компьютер
- **Модуль анонимизации** подготовлен на случай будущего подключения облачных провайдеров — текст будет предварительно анонимизирован перед отправкой
- **Конфигурация** хранится локально в `~/.yurteg/settings.json`
- **Файлы не загружаются на серверы** — обработка полностью локальная

### 9.5. Конфигурация

Централизованное управление настройками через `Config` dataclass:
- Персистентное хранение: `~/.yurteg/settings.json`
- Значения по умолчанию в dataclass
- Невалидные значения корректируются автоматически в `__post_init__`
- Рантайм-переопределения через `load_runtime_config(**kwargs)`

## 11. Сборка и дистрибуция

### 11.1. macOS

- Сборка через PyInstaller в нативное приложение (.app)
- Упаковка в DMG-образ (~232 МБ)
- Включает: Python-рантайм, все зависимости, статические ресурсы
- Генерация иконки приложения: `assets/icon_gen.py`
- Генерация фона DMG: `assets/dmg_background_gen.py`

### 11.2. Управление llama-server

При первом запуске Система:
1. Определяет платформу (macOS ARM / x86)
2. Скачивает соответствующий бинарник llama.cpp (релиз b5606)
3. Скачивает модель `yurteg-v3-Q4_K_M.gguf` (~1.5 ГБ) с HuggingFace
4. Сохраняет в `~/.yurteg/`

При каждом запуске приложения:
- llama-server стартует автоматически (`_start_llama`)
- Health-check подтверждает готовность модели
- При завершении приложения llama-server корректно останавливается (тройная защита)

## 12. Оценка рисков и план митигации

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Низкое качество извлечения локальной моделью | Средняя | Высокое | Файнтюнинг на юридических данных (выполнен — v3); GBNF-грамматика гарантирует JSON-схему; постобработка нормализует артефакты |
| Модель не помещается на устройстве пользователя | Низкая | Среднее | Квантизация Q4_K_M (~1.5 ГБ); архитектура допускает подключение облачных провайдеров |
| Пропуск персональных данных при анонимизации | Низкая | Низкое | Трёхпроходная NER-стратегия; 9 категорий regex-паттернов; консервативный принцип. Риск минимален, так как обработка полностью локальная — данные не покидают устройство |
| Ложные срабатывания анонимизации | Средняя | Низкое | Контекстная фильтрация (паспорт ≠ технический паспорт, ИНН ≠ сумма); при локальной модели анонимизация не применяется |
| Сбой llama-server | Низкая | Высокое | Тройная защита при завершении; health-check при старте; автоматический перезапуск |
| Повреждённые или нечитаемые файлы | Высокая | Низкое | Graceful degradation: пометка status=error, продолжение обработки; детальный лог |
